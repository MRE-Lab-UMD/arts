ARTS Software Architecture Proposal

From a dual-arm open resection system (ROS 2 Humble + OROCOS) to ARTS — a replicable, <$150k, fully open 3-arm laparoscopic platform for surgical autonomy research. Grounded in the v1.4 codebase inventory · August 2026.

Target runtime architecture

Everything above the real-time core is soft real-time and replaceable; everything inside it runs in a single process on the patient-cart PC so all three arms share one deterministic update cycle.

Retiring OROCOS — what replaces each piece

Today the OROCOS mid-level controller (the v1.4 controller) runs a 100 Hz activity with Reflexxes Type II and KDL, deployed through a .ops script, and requires hand-built RTT typekits for every message plus a serialized single-worker build of orocos_ws. Each RTT feature maps cleanly onto a maintained mainstream replacement:

OROCOS feature used in v1.4Replacement in ARTS
TaskContext with 100 Hz periodic activitycontroller_manager update loop at 250–500 Hz, SCHED_FIFO thread
Reflexxes Type II online trajectory generationRuckig (community version, actively maintained, jerk-limited OTG)
KDL FK / IK solversPinocchio (analytic derivatives, needed anyway for the RCM/collision QP); ur_ikfast kept for analytic IK
RTT ports + typekits for zero-serialization dataflowChainable-controller interfaces inside one process; intra-process composable nodes elsewhere — no typekit generation ever again
deployer + .ops deployment scriptsROS 2 launch + lifecycle nodes
OCL NetCDF reportingrosbag2 MCAP
Lock-free RT-safe buffersrealtime_tools RealtimeBuffer / RealtimeBox
The nuance worth keeping What OROCOS actually bought you was deterministic in-process dataflow between components. Preserve that property architecturally — keep each servo pipeline in-process with chained controllers, in two rate-grouped controller_managers (500 Hz for the UR5e pair, 125 Hz for the CB3 camera arm; the UR driver's blocking RTDE read forbids mixing rates in one loop) — rather than by keeping RTT. Note that the orocos_kdl kinematics library is a separate, still-maintained project; using or dropping it is independent of dropping the RTT runtime.
Why not keep RTT? To be clear, OROCOS RTT and rtt_ros2_integration are fully open source (Apache-2.0) — the objection is purely maintenance and community. rtt_ros2_integration has no formal releases and a contributor pool of a handful of people, and it is the single biggest build complexity in the legacy installer today (serialized single-worker builds, hand-generated typekits for every message). For a release aimed at replication by other labs, every dependency should be apt/rosdep-installable and familiar to contributors.
Determinism, the NVIDIA driver, and the RT kernel Important decoupling: neither OROCOS nor ros2_control makes timing deterministic by itself — both just run SCHED_FIFO priority threads, and the jitter floor comes from the kernel underneath. So the RTT-vs-ros2_control choice is orthogonal to the NVIDIA-on-PREEMPT_RT problem. That problem now has three workable answers, in order of preference: (1) keep the control path GPU-free so the control PC does not need the NVIDIA kernel module at all (GPU perception on a second machine or a non-RT box); (2) run a single PC without PREEMPT_RT — a lowlatency/PREEMPT_DYNAMIC kernel with SCHED_FIFO threads and isolcpus CPU shielding holds sub-millisecond jitter, which servoj's lookahead smoothing absorbs easily at 500 Hz; (3) if hard RT is truly wanted on the GPU machine, NVIDIA driver 590.44.01+ contains the locking fix that previously deadlocked PREEMPT_RT (unsupported officially, but functional). ARTS should be designed to work under option 1 or 2 and treat PREEMPT_RT as an optional tuning step.

Workspace layering & repo layout

ARTS keeps the proven v1.4 layering: a binary base underlay, categorized middle overlays for third-party stacks that ship in their own native layout, one first-party workspace on top, and per-project application overlays above that. End users never see the middle-overlay details — they source one setup.bash and build on top.

A terminology note that matters for newcomers: in ROS 2, underlay conventionally means the base installation you build on top of (/opt/ros/humble). The categorized third-party workspaces in the middle are therefore called middle overlays — each is an overlay of the base and an underlay for arts_ros2_ws. Calling them "underlays" invites confusion with the base, so ARTS does not.

Three rules keep this modular instead of fragile: (1) middle overlays never depend on each other, so they rebuild independently — enforced by building each in a fresh env -i shell that sources only the base, exactly as the legacy installer does; (2) every middle overlay is defined by a version-pinned vcstool .repos manifest stored in the arts repo (under middle_overlay_ros2_wss/), so the whole chain is reproducible with one assemble script; (3) if a middle overlay is ever rebuilt, everything above it rebuilds too (ABI safety) — acceptable because pinned overlays change perhaps once a year. A bonus below in Distribution: each middle overlay maps one-to-one onto a cached Docker image layer.

There are two trees, and conflating them is the most common source of confusion. The git repo holds only text — install recipes, vcstool manifests, and first-party source (tens of MB). Everything heavy — OEM SDK trees, third-party source, and build artifacts, roughly 142 GB on the current development PC — lives in a machine-local tree at ~/arts_local that is reconstructed from those recipes and never committed. The two trees mirror each other by folder name, so ~/arts/oem_drivers/spinnaker/install.sh installs into ~/arts_local/oem_drivers/spinnaker-4.2.0.88/.

Every non-package directory in the repo carries a COLCON_IGNORE marker so a colcon build from arts_ros2_ws does not descend into workspaces that must be built separately. This is mandatory in reference/ in particular: without it colcon follows the v1.4 reference symlink and attempts to build the entire previous-generation system. Note that COLCON_IGNORE is not .gitignore — those directories are fully git-tracked.

Two naming decisions worth stating explicitly. First, there is no arts_ur or arts_camera_flir package: UR and FLIR already have maintained third-party ROS drivers that arrive through the middle overlays, so what ARTS adds is launch and configuration, which lives in arts_driver. Only hardware with no ROS driver at all — the da Vinci disc drive, the ESU microcontroller, the Haply service bridge — earns a first-party package under arts_embedded/ (custom PCB + ESP32/micro-ROS bridges). Second, procedure-specific autonomy (perception, resection planners, task state machines) deliberately does not live in arts_ros2_ws; it belongs in application overlays. The prior system mixing ismr2024 and iros_2024_nephrectomy into its main repo is the pattern this avoids, and it is what makes the platform cleanly releasable.

Dependency pinning policy

An unpinned open-source dependency will break the build between machines or overnight. This is not hypothetical for this lab: during prior development, collision-detection code that built successfully one evening failed the next morning on a second PC because coal's API had changed upstream in between. With more than a hundred libraries in the chain, tracking HEAD is not viable — the rule is to pin a release that is verified to build, and stay on it until a concrete problem forces a bump.

Two rules deserve emphasis. Never a branch: version: main or devel in a .repos file is banned; use a tag or, preferably, a full commit hash. Non-ROS C++ libraries are pinned too — coal, pinocchio, proxsuite, and Ruckig each get their own build recipe, and any transitive FetchContent(… GIT_TAG main) hidden inside a dependency's CMakeLists is overridden explicitly rather than inherited. Bumping a pin is a deliberate, benchmarked act: change the version, rebuild, re-run that module's benchmark, and commit the new baseline beside the old one.

Cart naming

Keep the da Vinci-familiar names — they are instantly understood by every clinical and surgical-robotics reader: Patient Cart, Surgeon Console, Vision Cart. Inventing new names would cost recognition and buy nothing. In code they appear only as deployment profiles: cart-patient, cart-surgeon, cart-vision.

Answer to the "bridge to ROS and save, or just save?" question Bridge to ROS and record with rosbag2/MCAP. The thing that makes camera data hard to sync is not where you save it — it is where the timestamp comes from. With PTP-disciplined hardware stamps written into header.stamp by the Spinnaker ROS driver (as a composable node with intra-process transport, so frames are not copied), the bag is exactly as well-synchronized as a custom saver, and you keep one uniform recording, replay, and tooling path for every sensor in the system.

Recording architecture

Humble caveat: MCAP is supported but not the default rosbag2's MCAP plugin is officially released for Humble (ros-humble-rosbag2-storage-mcap) but is not part of the desktop/base variants and sqlite3 stays Humble's default — MCAP only became the default in Iron. So: install the plugin explicitly in every recording image and installer, always pass -s mcap to ros2 bag record, and put writer tuning (chunk size, zstd presets) in a shared --storage-config-file YAML. Playback needs no flag — rosbag2 auto-detects the format when reading.

Run two recorder processes into one session directory: bag A for robot/teleop/tool/energy state (~10 MB/s total — three arms at 500 Hz is trivial) and bag B for images, writing to a dedicated NVMe. MCAP with zstd for bag A; images stored uncompressed-by-rosbag (already Bayer or JPEG). Footpedal events publish "episode start/stop" marks that the recorder logs, so demonstrations segment themselves. Offline, arts_datasets aligns streams by hardware stamps and exports LeRobot-format episodes for SRT-H training.

Distribution: Docker-first, host-setup second

The install-script pain from the prior system (OEM drivers pinned to specific releases, deps breaking overnight) is exactly what container images solve: users pull a frozen, tested image instead of re-resolving the world. But a container cannot provide kernel or clock discipline, so the design is a thin host layer plus fat images. The workspace layering maps one-to-one onto Docker image layers: each middle overlay (ur_ros2_ws, flir_ros2_ws, slicer_ros2_ws, oem_ros2_ws) is built in its own layer, so changing arts code rebuilds only the top layer while every middle overlay stays cached.

Stays on the host host_setup.sh

· CPU isolation (isolcpus for the control core); PREEMPT_RT kernel optional per decision 8

· ptp4l / phc2sys PTP grandmaster config

· NIC tuning: jumbo frames, receive buffers for GigE Vision

· udev rules (Haply, MCU serial, cameras), NVIDIA driver, nvidia-container-toolkit

Lives in containers GHCR images

· arts-control — net=host, CAP_SYS_NICE, /dev access; runs controller_manager

· arts-vision — NVIDIA runtime, Spinnaker, perception models

· arts-teleop / arts-recorder / arts-slicer (X11) / arts-sim (Isaac Lab)

· devcontainer for contributors, same base image as release

Redistribution check before release Spinnaker SDK, the Haply Inverse Service, and Zivid debs have OEM licenses that may not permit baking into a public image. The pattern that always works: the Dockerfile takes the vendor archive as a build argument, the repo documents the (free) download step, and your lab additionally keeps the current Software/-style vendored mirror for internal builds. Everything else should come from rosdep/apt with versions pinned in the image.

Keep a bare-metal install path, but generate it from the same Dockerfile layers (or document the Dockerfile as the canonical install recipe) so the two never drift apart the way the existing install docs and scripts already have.

Module-first development workflow

The host stays minimal — kernel, NVIDIA driver, docker + nvidia-container-toolkit, PTP daemons — and every module is developed and benchmarked in its own compose profile with only its driver and ROS wrapper installed. The benchmark harness is a contract every driver package honors: a bench launch file plus an offline analyzer that reports achieved rate (mean ± std from MCAP stamps), CPU%, RSS, disk/network I/O, and drop count. Each result is committed under docs/benchmarks/ together with the image digest it ran on, so baselines are reproducible and regressions are diffable.

Integration then climbs a ladder, re-running the identical benchmarks at every rung: (1) module solo; (2) contention pairs — both cameras together, cameras + recorder, arms + recorder; (3) full patient cart; (4) full system with teleop and display. Each module also gets a resource budget up front (CPU cores from the isolcpus map, NIC allocation for GigE cameras, NVMe lane for the image bag) so a benchmark passes against its budget, not just in isolation.

PREEMPT_RT + NVIDIA + isolcpus — single-PC RT PROVEN (2026-08-05) Ubuntu Pro realtime kernel 5.15.0-1081-realtime installed as a second GRUB entry (generic 6.8.0-136 kept). NVIDIA driver 595.84 installed via apt install nvidia-driver-595 (userspace) + IGNORE_PREEMPT_RT_PRESENCE=1 DKMS bypass (made permanent in /etc/dkms/framework.conf; packages held via apt-mark hold). CPU isolation: isolcpus=4,5,10,11 nohz_full=4,5,10,11 rcu_nocbs=4,5,10,11 in GRUB. cyclictest result (5 min, CPU saturated + NVIDIA GPU rendering via PRIME offload): worst-case latency on isolated cores = 190 µs (avg 4–5 µs). That is 9.5% of the 500 Hz control period (2 ms) — well within budget. Decision 8 is answered: single-PC RT is the path forward; the two-PC and lowlatency-baseline fallbacks are retired. Production workstation with 16+ cores will have even more isolation headroom.

New components not in the prior system

Software remote center of motion (RCM) arts_controllers
Formulate the servo loop as a small QP solved every cycle (pinocchio for kinematics + derivatives, proxsuite as solver): primary task tracks the tool-tip pose command; equality/soft constraint pins the instrument shaft to the calibrated cannula point; inequality constraints enforce joint limits, velocity limits, and arm–arm minimum distance. This is the standard modern replacement for the mechanically-constrained RCM of the da Vinci, runs comfortably at 250–500 Hz for three 6-DoF arms, and subsumes the current Reflexxes+KDL pipeline. Calibrate each RCM point from the cannula pose in the trainer box; a later refinement can estimate the true fulcrum from interaction forces.
Real-time arm–arm collision detection and prediction arts_safety
Approximate arms, adapters, and instrument shafts as capsules and query distances with coal (already vendored in the prior system) at ≥200 Hz. Predict by rolling joint states forward 100–300 ms at current velocities. Feed the results into the same QP as velocity-damper inequality constraints, so arms smoothly slow and deflect near contact instead of e-stopping — essential when all three elbows crowd over one trainer box while the surgeon's attention is at the tool tips. Hard e-stop remains as the escalation path.
Haptic teleoperation arts_teleop
The Inverse3 talks through the Haply Inverse Service — an OEM driver in the same category as Spinnaker or the UR controller firmware: a closed binary with a fully documented, open JSON-over-WebSocket API and open-source clients (Haply's Rust crate, Isaac Lab's Python HaplyDevice class). Every existing open wrapper sits on this service, so ARTS wraps it too: a thin bridge node polls it at 500 Hz — matched to the UR5e RTDE rate; the service's multi-kHz capability is unnecessary here since the service answers one state per command sent. The teleop layer implements clutching, 3:1–5:1 motion scaling, and mapping into the camera frame (so surgeon hand motion matches the laparoscope view), then publishes Cartesian target topics consumed by the RT core. Operator inputs beyond the cursor need an explicit, configurable mapping layer: VerseGrip buttons and a programmable 3-pedal footswitch are assigned to clutch, camera control, instrument switching, energy activation, and recording marks via a single mapping file (not hardcoded). Haply's first-party Isaac Lab integration gives sim teleop nearly for free. One dependency note for the docs: unlike the UR driver (open PC-side code over a documented wire protocol), the Inverse3 serial protocol is not public, so the service binary is a hard dependency.
da Vinci X instrument drive arts_dv_tool_driver
The custom UR–da Vinci adapters need a 4-motor disc drive per instrument. Expose it as an ordinary ros2_control joint interface (wrist pitch/yaw + jaw) chained into the same controller_manager so tool wrist and arm motion are coordinated in one cycle. ARTS defines and publishes its own instrument kinematics/coupling files for da Vinci X instruments — deliberately independent of dVRK, which has no support path for Xi/X/SP/5-generation tools. Existing dVRK definitions serve as a cross-check reference at most.
Energy / footswitch microcontroller arts_esu
Run micro-ROS on the MCU that sits between footswitches, the ESU back panel, and the PC. It publishes activation state (who requested energy, when it actually fired) and accepts activation commands from software — both directions land in the same bag, so imitation learning gets exact energy-on/off labels aligned with images and kinematics.
Stereo display path (GOOVIS HMD) surgeon console
The GOOVIS is an HDMI display: render the two FLIR streams side-by-side with a dedicated low-latency GStreamer/GPU path directly from the camera driver, not through RViz. Target glass-to-glass latency under ~100 ms; this path is independent of the recording path so display never competes with the recorder.

Evaluation & benchmarking (ISMR target)

Every claim about the system gets a measurable, reproducible test — and where a comparison to dVRK or clinical systems is meaningful, the measurement method is independent of the software stack (external cameras, offline analysis of recorded stamps) so numbers are directly comparable across platforms.
